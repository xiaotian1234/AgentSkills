# 《Designing Data-Intensive Applications》第二版方法论存档

- 作者：Martin Kleppmann、Chris Riccomini
- 版本：第二版，O'Reilly，2026
- 调研截止：2026-09-17
- 版本说明：本 Skill 使用第二版 14 章结构，不沿用第一版章节编号

## 核心框架

### 1. 从非功能需求反推数据架构（第 1-2 章）

适用：数据库、缓存、消息、云服务和部署形态选型。

步骤：明确系统记录与派生数据；定义负载、延迟分位数、可靠性、故障模型、扩展方式、可运维性和可演进性；比较单节点、分布式、云和自托管方案；记录不可避免的权衡。

输出：负载模型、SLO、故障假设、数据流和技术权衡表。

### 2. 数据生命周期决策链（第 3-8 章）

适用：模型、存储、编码、复制、分片和事务设计。

步骤：按访问模式选择数据模型；按读写模式选择索引与存储；设计向前/向后兼容编码；选择复制拓扑和冲突语义；仅在容量或隔离确有需要时分片；按业务不变量选择隔离与事务机制。

输出：数据模型、索引、兼容策略、复制/分片方案、事务边界。

### 3. 在部分失败世界里追求可验证正确性（第 9-13 章）

适用：分布式锁、消息处理、数据同步、批流一体和派生数据。

步骤：假定网络、时钟和进程会部分失败；明确一致性要求；区分线性一致、事务隔离和共识；用幂等、日志、端到端校验与重放管理派生状态；对“恰好一次”承诺检查其端到端边界。

输出：故障矩阵、一致性模型、消息语义、重放和校验策略。

## 决策规则

1. 如果没有负载参数和延迟分位数，就不能声称系统“可扩展”或“高性能”。（第 2 章）
2. 如果数据模型与主要访问路径不匹配，则不要用熟悉度决定数据库类型。（第 3 章）
3. 如果系统需要长期演进，则编码格式和 API 必须定义前向、后向兼容策略。（第 5 章）
4. 如果读取副本可能滞后，则明确是否需要 read-your-writes、monotonic reads 等保证。（第 6 章）
5. 如果数据量和租户隔离尚不要求分片，则不要提前承担重平衡、热点和二级索引成本。（第 7 章）
6. 如果业务不变量会被并发写破坏，则检查隔离级别，不要只依赖“使用了事务”。（第 8 章）
7. 如果算法依赖超时、时钟或锁，则按网络延迟、进程暂停和租约失效分析。（第 9 章）
8. 如果需要全局顺序或唯一领导者，则明确是否真正需要线性一致或共识，并接受可用性与延迟代价。（第 10 章）
9. 如果数据库和消息系统共同更新，则验证端到端幂等与一致性，不轻信局部“恰好一次”。（第 8、12-13 章）
10. 如果多个专用系统组合成数据流，则把系统记录、派生数据、重建路径和校验方式写清楚。（第 11-13 章）

## 数据架构检查清单

- [ ] 系统记录和所有派生数据已区分。
- [ ] 读写负载、热点、增长率和延迟分位数已量化。
- [ ] 硬件、软件、网络、时钟和人为故障已建模。
- [ ] 数据模型与访问模式一致，索引成本已考虑。
- [ ] 编码、接口和模式演进有兼容策略。
- [ ] 复制延迟、冲突和故障切换语义明确。
- [ ] 分片键、热点、重平衡和二级索引方案明确。
- [ ] 事务隔离级别能保护业务不变量。
- [ ] 消息幂等、重复、乱序、重放和死信策略明确。
- [ ] 派生状态可以重建并进行端到端校验。

## 反模式

1. 按技术标签选型：因为“云原生”“NoSQL”或“微服务”而选，不先写需求。（第 1-3 章）
2. 用平均延迟掩盖尾部延迟。（第 2 章）
3. 把复制当备份，忽视逻辑错误会同步传播。（第 6 章）
4. 把 ACID 当作单一保证，忽略隔离级别和实现差异。（第 8 章）
5. 假设网络可靠、时钟准确、进程不会长暂停。（第 9 章）

## 边界

- 本书面向数据密集型系统；单机实时图像处理和设备控制不一定需要分布式技术。
- 第二版讨论 2026 年技术生态，但厂商产品能力、价格和 SLA 必须查当前官方资料。
- 书中帮助理解原理和权衡，不替代针对具体数据库的容量测试与故障演练。
- 第 14 章涉及数据伦理与责任，不能替代法律和合规意见。
