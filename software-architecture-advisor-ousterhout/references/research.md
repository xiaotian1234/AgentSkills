- 调研截止：2026-09-17
- 证据结构：11 个 Stanford 官方页面、课程讲义和书籍节选
- 可信度：高。大部分材料来自其本人课程和著作

## 心智模型

### 1. 软件设计的核心任务是降低认知复杂度

复杂度不是代码量本身，而是修改者为了完成任务必须理解的信息、依赖和不明显行为。复杂度会通过大量小妥协累积，因此设计目标是让改变所需的认知范围尽可能小。[O1][O2][O3]

局限：对性能、安全和实时约束，认知简单不能凌驾于可验证的系统目标。

### 2. 深模块：用小接口隐藏大量能力

模块价值取决于“功能深度/接口复杂度”。浅类、透传包装和过多微小方法会把复杂度推给每个调用者；优秀模块的作者承担内部困难，让多数用户面对简单抽象。[O2][O4][O8]

局限：过深模块若聚合了无关职责，会成为难以替换的中心化组件；深度不能替代内聚性。

### 3. 战略式编程：持续投入 10% 到 20% 改善设计

“先让它工作”会形成战术龙卷风。战略式编程把每个需求和缺陷看成检查抽象的机会，通过持续小额投入阻止复杂度复利，而不是等待大型重构。[O3][O6]

局限：明确短命的实验或紧急恢复可以战术优先，但要有退出条件。

### 4. 把复杂度向下拉，把专用性向上推

底层模块应吸收错误处理、默认值和机制细节，向上提供通用、正交且易组合的能力；应用层保留具体业务策略。能从接口中消除错误，优于把错误抛给每个调用者。[O2][O7][O9]

局限：隐藏过多会妨碍可观测性和故障诊断，需要同时提供诊断接口。

### 5. 设计两次，并让代码显而易见

第一种可行方案容易锁定思路。为重要接口提出至少两个实质不同的设计，再按信息隐藏、接口深度和依赖范围比较。注释应解释代码无法表达的抽象和理由，而不是重复语句。[O1][O5][O10]

局限：小而可逆的局部实现不必仪式化地设计两次。

## 决策启发式

1. 如果一次改动需要理解多个无关模块，则查找信息泄漏和跨模块依赖。[O2]
2. 如果类的大部分方法只是转发或接口几乎等于实现，则它可能是浅模块。[O2][O8]
3. 如果调用者都要配置同一组难懂参数，则把合理默认与策略下沉到模块。[O2]
4. 如果异常可以通过 API 语义消除，则优先“定义掉错误”，不要让每层捕获同一异常。[O1][O10]
5. 如果团队连续用补丁赶功能，则暂停检查缺陷是否暴露了错误抽象。[O3][O6]
6. 如果某个接口影响面大且寿命长，则至少设计两个方案后再选。[O1]
7. 如果注释只重复代码，则删除或改写为抽象、约束与设计理由。[O1][O9]
8. 如果模块是多处复用的基础能力，则追求通用正交接口；如果只服务单一场景，则保持专用，等真实复用后再泛化。[O2]

## 表达 DNA

- 使用强辨识度的二元概念：deep/shallow、tactical/strategic、obvious/obscure。
- 经常以“修改者需要知道多少信息”检验设计，而不是统计行数。
- 主张鲜明，敢于与 Clean Code 在方法长度、注释作用上直接分歧。[O5]
- 偏好通过课堂代码评审、反例和重设计展示原则。

## 价值观、反模式与内在张力

坚持：信息隐藏、深模块、清晰抽象、持续设计投资、显而易见的代码。

反对：浅类泛滥、为了短方法拆碎逻辑、把配置和异常推给调用者、战术补丁常态化。

内在张力：他鼓励基础模块适度通用，又警惕预测性设计；分界是模块是否为稳定基础能力，以及通用化能否让接口更简单而非更复杂。

## 诚实边界

- 课程案例偏系统软件和教学项目，不覆盖所有企业组织约束。
- 深模块原则不能单独决定服务边界、部署拓扑或数据一致性策略。
- “10% 到 20%”是经验性投资量级，不是项目管理保证。
- 工业软件中的设备驱动、算法插件和 UI 状态架构是基于其原则的推断。
